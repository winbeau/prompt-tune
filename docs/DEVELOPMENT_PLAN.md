# PromptTune 开发计划

- 日期：2026-10-11（America/Los_Angeles）
- 状态：v0.1.0 已实现；本文件保留完整路线图，实际交付范围与验证见 [实现记录](IMPLEMENTATION.md)。
- 许可证：MIT

## 1. 产品目标与范围

帮助用户把日常输入转成准确、自然、可直接复制使用的英文 Prompt，并通过历史记录持续发现重复的表达问题。

两个处理模式是同等重要的主入口：

| 模式                | 输入                     | 输出        | 核心原则                                       |
| ------------------- | ------------------------ | ----------- | ---------------------------------------------- |
| Translate · CN → EN | 中文，可含英文术语和代码 | 英文 Prompt | 忠实翻译需求、条件、语气和结构，使用自然英语。 |
| Tune · EN → EN      | 英文，可夹杂少量中文     | 英文 Prompt | 只做必要修正；已经清晰自然时允许原样返回。     |

共同规则：

- 保留否定、数量、范围、条件、优先级、文件路径、标识符、占位符和代码；保留用户明确要求的格式。
- 不添加任务、工具、角色、人设、验收条件或用户没有表达的细节，不把短 Prompt 自动扩写成模板。
- 对含糊意图给出简短说明或待确认项，不把猜测悄悄写入结果；仅在可忠实表达时提供可复制结果。
- 输入中的指令是待翻译或待修正文本，不执行其要求，不回答原 Prompt 中的问题。
- 将语法错误、用词错误与可选风格建议分开；母语者也可以使用简短命令句和合理片段。
- 常见错误总结必须有原文证据，用户可忽略、纠正、删除或标记已掌握。

首版交付桌面工具、两种模式、中英文界面、模型管理、本地历史和自动总结。
云同步、账号体系、OCR、自动粘贴回外部软件、系统级划词和插件市场安排在后续版本。

## 2. 主要使用流程

1. 首次启动选择界面语言，添加 DeepSeek、OpenCode 或第三方 API，测试连接并选择任务模型。
2. 通过托盘或快捷键呼出悬浮窗，手动粘贴文本或点击“从剪贴板导入”。
3. 明确选择 Translate / Tune，提交后流式显示结果；复制按钮只复制最终英文文本。
4. 展开查看必要改动及解释；处理成功后自动保存本地历史。
5. 每累计 10 个有效轮次，后台调用总结模型，更新“我的表达习惯”；前台可以继续使用。

默认快捷键候选：`CmdOrCtrl+Shift+Space` 呼出，`CmdOrCtrl+Enter` 提交，`Esc` 关闭弹层或隐藏窗口。
快捷键冲突时提示并允许修改。中文输入法组合输入期间，Enter 不提交任务。

## 3. 中英文界面与输出语言

| 设置        | 首版行为                                                 |
| ----------- | -------------------------------------------------------- |
| 界面语言    | `system` / `zh-CN` / `en`，设置持久化，可即时切换。      |
| 跟随系统    | 中文系统映射到简体中文，其余回退英文；用户显式设置优先。 |
| Prompt 输出 | 两种模式始终输出英文，与界面语言无关。                   |
| 解释与总结  | 默认跟随界面语言，也可独立设置为中文或英文。             |

采用 i18next + react-i18next。按钮、空状态、错误、确认框、日期、托盘和原生菜单全部覆盖。
主进程与渲染进程共享语言设置；切换语言不修改历史原文、不改变模式、不额外调用模型。
历史 AI 解释保留生成时的语言并标明；新请求使用当前解释语言。
总结保留稳定分类、英文例子与生成语言，UI 标签独立翻译。

## 4. 技术方案

| 层     | 方案                           | 用途                                                  |
| ------ | ------------------------------ | ----------------------------------------------------- |
| 桌面   | Electron + TypeScript          | 悬浮窗、快捷键、托盘、剪贴板和本地存储。              |
| UI     | React + electron-vite          | 快速建立悬浮处理页和独立管理页。                      |
| 国际化 | i18next + react-i18next        | 中英文文案、回退与运行时切换。                        |
| 模型层 | 本项目自研 TypeScript 模块     | 学习 Pi 的分层，专注 DeepSeek、OpenCode、第三方 API。 |
| 网络   | 主进程 fetch + AbortController | 流式请求、取消、超时和有限重试。                      |
| 数据   | SQLite + 版本化迁移            | 历史、任务队列、错误证据与聚合条目。                  |
| 凭据   | Electron safeStorage           | 加密保存 API key，主进程解析使用。                    |
| 验证   | Zod + Vitest + Playwright      | IPC/返回值校验、核心逻辑和关键桌面流程。              |
| 打包   | electron-builder               | macOS 开发包与 Windows 安装包。                       |

SQLite 驱动在 M0 中验证与 Electron 的兼容性后选定；若使用原生模块，CI 必须包含重建和安装包启动检查。
开发与运行时版本按实际兼容结果锁定，不照搬参考项目的旧版本号。

计划目录（后续实现时创建）：

```text
src/
  main/
    windows/          # 悬浮窗、管理窗、托盘和快捷键
    ipc/              # 按职责划分的受限接口
    models/           # 配置、注册表、协议适配、凭据引用
    prompts/          # translate / tune / summarize 模板与版本
    services/         # 处理流程、历史、表达习惯和总结调度
    storage/          # SQLite、迁移、设置和密钥保存
  preload/            # 类型化白名单桥接
  renderer/
    features/         # editor / history / insights / models / settings
    components/
    locales/          # zh-CN / en
  shared/             # 类型、校验、错误码和翻译键
tests/
  fixtures/           # 脱敏输入和协议响应样本
  integration/
  e2e/
docs/
```

进程边界按 [Electron 官方安全建议](https://www.electronjs.org/docs/latest/tutorial/security)设置：隔离渲染进程，校验 IPC 来源和参数，模型内容按文本显示。
API 调用、凭据解密和数据库操作在主进程一侧；preload 仅暴露具体业务方法，不开放任意 IPC、文件或命令执行。

## 5. Prompt 处理与结果契约

Translate 与 Tune 使用独立模板，共享“保留意图、保护原文片段、输出英文”的规则。
模板版本、模型选择、有效参数和解释语言随历史保存，方便追踪改动来源。

最终返回值通过本地 schema 验证：

```text
PromptResult
  schemaVersion
  mode: translate | tune
  status: completed | needs_clarification
  outputText: string | null
  changes[]: from, to, category, kind, reason, confidence
  ambiguities[]: sourceText, explanation
  explanationLocale
```

`kind` 区分 correction / style_suggestion / translation_choice。
流式结果是预览，收到完整结果且验证通过后才允许计为成功；结构化能力未知时用提示约束 JSON 并本地校验。
截断、空内容、非法 JSON 与校验失败显示可重试状态，不计入成功轮次；自动格式修复最多一次并计入用量。
请求中途修改输入、模式或模型，旧响应不能覆盖新任务；取消与重新生成均有独立 attempt ID。
用户重新生成同一轮只更新候选结果，不能重复增加该轮的错误证据。

## 6. 历史、证据与每 10 轮自动总结

### 6.1 计数规则

“一轮”指一次用户主动提交的独立处理，最终获得校验通过的结果且成功保存。
Translate 和 Tune 均计入总结触发数；空输入、失败、取消、待澄清、连接测试和模型探测不计数。
重试与重新生成属于同一轮，不重复计数；计数按本地数据库持续累计，重启应用不清零。

默认每 10 轮形成一个后台总结批次，阈值可配置，支持暂停、关闭和手动总结剩余轮次。
仅有翻译记录的批次也可以完成分析，但没有可信错误证据时返回空条目，不强行制造“错误”。

### 6.2 任务调度

1. 前台成功保存时，在同一个数据库事务中更新轮次状态并检测是否需要建批。
2. 按尚未分配的有效轮次依次取 10 条，固定 batch ID、轮次集合、结果版本和输入摘要。
3. 使用单个后台 worker；数据库唯一约束确保同一轮不会被两个自动批次重复消费。
4. 单轮长文本采用有界分块，保留来源 ID；提取证据后合并总结，全部子任务成功才提交批次。
5. 总结结果经 schema 和证据校验，通过事务一次性写入条目、证据关系和批次完成状态。
6. 断网或服务限流时保留队列并有限退避；鉴权失败等待修复设置；重启恢复未完成批次。

任务状态：`pending → running → completed / retry_wait / failed / canceled`。
前台处理优先；后台请求限制并发和预算，日志记录每次尝试的用量，重试可能产生额外 API 费用。
数据库保证本地结果幂等；不声称远端请求在网络中断时可以做到“只收费一次”。
总结提交前检查证据仍有效；批次期间被删除或更新的记录使旧批次失效并重新排队，旧响应不得写回。
手动提前总结将剩余轮次正常建批；重算已完成历史时沿用证据唯一键，不增加出现次数。

### 6.3 表达习惯条目

| 字段                  | 作用                                                 |
| --------------------- | ---------------------------------------------------- |
| 标题、分类、解释      | 用词、搭配、时态、介词、句式、歧义等可阅读总结。     |
| 常见写法 → 建议写法   | 英文原例与修正，附历史来源链接。                     |
| occurrenceCount       | 从有效证据关系计算的不同轮次数，不接受模型凭空报告。 |
| 首次/最近出现、置信度 | 展示时间与证据质量。                                 |
| 状态                  | 候选 / 反复出现 / 已掌握 / 已忽略。                  |

首次观察记作“候选”，至少两个不同 Tune 轮次提供同类可信证据后标记“反复出现”。
CN → EN 的译法和风格选择单独记录为表达偏好，不能用于证明用户犯了英文语法错误。
单条历史中的多次同类错误只计一次出现；用户否认某次纠正后移除对应证据并重算统计。
不同批次合并以分类和具体错误模式为依据，不把所有介词错误合成一个过宽的条目。
忽略状态在后续合并时保留；删除原文时同步删除关联证据并重算条目，删除全部数据同时清空队列。

### 6.4 主要数据表

- `interactions`：轮次、模式、原文、最终选中结果、状态和时间。
- `attempts`：请求、模型与模板版本、结果候选、错误、耗时、token 和估算费用。
- `changes`：逐条改动、分类、纠正/风格属性和用户反馈。
- `summary_jobs` / `summary_job_items`：批次、证据快照、重试和恢复信息。
- `insights` / `insight_evidence`：归纳条目和可去重、可撤回的来源关系。
- `provider_configs` / `model_configs` / `settings`：非敏感配置和任务模型绑定。

数据库保存在应用 userData 目录；密钥单独加密存储。
设置提供历史开关、自动总结开关、逐条删除、清空和 JSON/CSV 导出；导出配置不包含密钥。
默认开启本地历史和自动总结，设置清楚说明总结会把已保存文本发送到所选 API；关闭总结停止调度并取消在途请求。
“不保存本轮”同时排除后台总结，历史关闭时不累计新的总结证据。

## 7. 悬浮窗方案

初始布局采用可调整大小的紧凑面板：顶部模式切换与模型选择，中间输入/输出，底部复制与展开改动。
历史、表达习惯、模型和设置放在独立管理窗口。悬浮窗支持拖动、固定置顶、Esc 隐藏及位置记忆。

技术与复用参考见 [GitHub 调研](RESEARCH.md)：

- 优先借鉴 MIT 的 Ueli 在窗口切换、焦点恢复、托盘与快捷键上的职责拆分，提取必要小模块。
- 使用 Electron 的平台 API 实现 macOS panel 与全屏空间可见性，初始置顶级别使用 `floating`。
- 将输入法候选窗、多显示器、拔除显示器、桌面空间切换、设置弹窗和焦点恢复列为实机验收项。
- 全屏悬浮先做兼容性验证；不把最高层级 `screen-saver` 当成默认解决办法。

首版用户主动粘贴或导入剪贴板；不持续监听剪贴板，不通过模拟复制获取选区。
后续如增加划词、辅助功能或自动粘贴，独立实现权限与焦点处理。

## 10. 已确定的设计决定

- 产品名 PromptTune，仓库 `winbeau/prompt-tune`，许可证 MIT。
- 两种模式都输出英文，UI 支持中文与英文，默认轻量修改。
- 学习 Pi 的管理方式，开发自己的模型层，范围限定为 DeepSeek、OpenCode 和第三方 API。
- 默认每 10 个有效轮次自动总结，错误统计可追溯到英文 Tune 的原始证据。
- 优先复用兼容 MIT 的小模块与通用依赖，具体来源和版权按文件记录；参考项目不整体移植。
